Retrieval Augmented Generation (RAG)

Memahami arsitektur RAG — teknik yang menggabungkan information retrieval dengan LLM untuk menghasilkan respons yang akurat dan berbasis data.

🎯 Tujuan Pembelajaran

  • Memahami definisi dan motivasi di balik RAG (halusinasi, knowledge cutoff, domain-specific)
  • Menguasai arsitektur RAG: indexing pipeline, retrieval pipeline, dan generation
  • Mampu menerapkan berbagai chunking strategies: fixed-size, semantic, dan recursive
  • Memahami alur embedding → vector store → retriever → generator
  • Menerapkan best practice chunking untuk optimal retrieval

📋 Kompetensi Dasar

  • Mampu menjelaskan bagaimana RAG mengatasi limitasi LLM
  • Mampu merancang indexing pipeline dengan chunking strategy yang tepat
  • Mampu memilih dan mengkonfigurasi retriever (similarity search, MMR, threshold)
  • Mampu membangun prompt template yang mengintegrasikan retrieved context

8.1 Definisi & Mengapa RAG Diperlukan

Definisi RAG

Retrieval Augmented Generation (RAG) adalah teknik yang menggabungkan information retrieval (pencarian informasi) dengan text generation LLM. Alih-alih hanya mengandalkan pengetahuan internal model (parameter memory), RAG mengambil dokumen-dokumen relevan dari knowledge base eksternal dan menyuntikkannya ke dalam prompt LLM sebagai konteks tambahan. Hasilnya: respons yang lebih akurat, faktual, dan dapat diverifikasi sumbernya.

📖 Analogi: RAG seperti "open-book exam" untuk LLM. Model tidak perlu menghafal semua pengetahuan dalam parameternya; cukup mencari di "buku referensi" (vector database) saat dibutuhkan.

Mengapa RAG Diperlukan?

Tiga masalah utama LLM yang diatasi oleh RAG:

🔴 Halusinasi (Hallucination)

LLM sering menghasilkan informasi yang terdengar meyakinkan tetapi faktanya salah. RAG menyediakan ground-truth dari dokumen sumber, secara drastis mengurangi halusinasi.

🟠 Knowledge Cutoff

LLM hanya mengetahui informasi sampai tanggal training cutoff-nya. RAG memungkinkan akses ke informasi real-time atau terbaru melalui knowledge base yang selalu diperbarui.

🔵 Domain-Specific Knowledge

LLM general-purpose tidak memiliki pengetahuan mendalam tentang domain spesifik (hukum, medis, internal perusahaan). RAG memungkinkan injeksi pengetahuan domain-spesifik ke dalam prompt.

Tanpa RAGDengan RAG
Hanya mengandalkan parameter modelMencari dokumen relevan dari knowledge base
Rentan halusinasiJawaban berbasis sumber yang dapat diverifikasi
Terbatas pada knowledge cutoffSelalu up-to-date dengan data terbaru
Tidak transparanDapat mencantumkan sumber (source attribution)

Use Cases RAG

📚 Document Q&A

Tanya-jawab dengan dokumen internal perusahaan

🤖 Customer Support Bot

Chatbot yang menjawab berdasarkan knowledge base produk

🏥 Medical Q&A

Asisten medis berbasis jurnal dan pedoman klinis

⚖️ Legal Research

Pencarian preseden hukum dari database kasus

💻 Code Assistant

Mencari codebase untuk menjawab pertanyaan developer

📊 Business Intelligence

Query data bisnis dengan natural language

8.2 Arsitektur RAG

Arsitektur RAG terdiri dari tiga pipeline utama yang bekerja bersama: Indexing Pipeline (offline), Retrieval Pipeline (online), dan Generation.

Indexing Pipeline diproses secara offline (batch): dokumen di-chunk, di-embedding, dan disimpan ke vector store. Retrieval Pipeline berjalan real-time: query user di-embedding, kemudian dilakukan similarity search ke vector store untuk mengambil top-K chunk paling relevan. Generation: chunk yang ter-retrieve disusun bersama query user ke dalam prompt template, lalu dikirim ke LLM untuk menghasilkan respons final.

8.3 Indexing Pipeline

Indexing Pipeline adalah proses mempersiapkan dokumen agar dapat di-retrieve secara efisien. Terdiri dari tiga tahap utama: Chunking → Embedding → Vector Store.

8.3.1 Chunking Strategies

Chunking adalah proses memecah dokumen panjang menjadi potongan-potongan kecil (chunks) yang dapat diproses oleh embedding model dan di-retrieve secara presisi.

a) Fixed-Size Chunking

Memecah dokumen berdasarkan jumlah karakter atau token tetap (misal: 512 token per chunk). Sederhana dan cepat, tetapi dapat memotong kalimat atau paragraf di tengah.

# Fixed-size chunking dengan overlap
def fixed_size_chunk(text, chunk_size=512, overlap=50):
    chunks = []
    start = 0
    while start < len(text):
        end = start + chunk_size
        chunk = text[start:end]
        chunks.append(chunk)
        start = end - overlap  # overlap untuk menjaga konteks
    return chunks

# Contoh penggunaan
text = "Dokumen panjang tentang AI..."
chunks = fixed_size_chunk(text, chunk_size=512, overlap=50)
print(f"Jumlah chunks: {len(chunks)}")
📌 Overlap: Overlap (tumpang tindih) antar chunk memastikan tidak ada informasi yang hilang di batas pemotongan. Overlap 10-20% dari chunk size adalah rekomendasi umum.

b) Semantic Chunking

Memecah dokumen berdasarkan batas semantik alami seperti paragraf, section header, atau perubahan topik. Menggunakan embedding similarity untuk mendeteksi "breakpoint" semantik.

# Semantic chunking berdasarkan embedding similarity
from sklearn.metrics.pairwise import cosine_similarity
import numpy as np

def semantic_chunk(sentences, embeddings, threshold=0.5):
    chunks = []
    current_chunk = [sentences[0]]
    
    for i in range(1, len(sentences)):
        similarity = cosine_similarity(
            [embeddings[i-1]], [embeddings[i]]
        )[0][0]
        
        if similarity < threshold:  # topik berubah
            chunks.append(" ".join(current_chunk))
            current_chunk = [sentences[i]]
        else:
            current_chunk.append(sentences[i])
    
    if current_chunk:
        chunks.append(" ".join(current_chunk))
    return chunks

c) Recursive Chunking

Menggunakan separator hierarkis untuk memecah teks. Mulai dari separator terbesar (misal: "\n\n" untuk paragraf), jika masih terlalu besar, lanjut ke separator lebih kecil ("\n", ". ", " ").

# Recursive character text splitting (seperti LangChain)
def recursive_chunk(text, chunk_size=512, chunk_overlap=50,
                    separators=["\n\n", "\n", ". ", " ", ""]):
    # Gunakan separator pertama yang cocok
    for sep in separators:
        if sep == "":
            # Fallback: split per karakter
            chunks = [text[i:i+chunk_size] 
                      for i in range(0, len(text), chunk_size - chunk_overlap)]
            return chunks
        
        splits = text.split(sep)
        if len(splits) > 1:
            # Rekursif: gabungkan split yang < chunk_size
            result = []
            current = ""
            for split in splits:
                if len(current) + len(split) + len(sep) <= chunk_size:
                    current = (current + sep + split) if current else split
                else:
                    if current:
                        result.append(current)
                    current = split
            if current:
                result.append(current)
            return result
    
    return [text]

8.3.2 Embedding

Setiap chunk dikonversi menjadi vector embedding menggunakan embedding model (seperti yang dibahas di BAB 6). Embedding ini merepresentasikan makna semantik chunk dalam ruang vektor berdimensi tinggi.

from openai import OpenAI
client = OpenAI()

def embed_chunks(chunks, model="text-embedding-3-small"):
    embeddings = []
    for chunk in chunks:
        response = client.embeddings.create(
            model=model,
            input=chunk
        )
        embeddings.append(response.data[0].embedding)
    return embeddings

chunks = ["Chunk 1 tentang AI...", "Chunk 2 tentang ML..."]
embeddings = embed_chunks(chunks)
print(f"Dimensi embedding: {len(embeddings[0])}")  # 1536

8.3.3 Vector Store

Embedding disimpan di vector database (Pinecone, Weaviate, Qdrant, Chroma, Milvus, FAISS) bersama metadata dan teks asli chunk. Vector store memungkinkan pencarian berbasis similarity yang cepat.

import chromadb

client = chromadb.Client()
collection = client.create_collection(name="knowledge_base")

# Simpan chunks + embeddings + metadata ke vector store
for i, (chunk, embedding) in enumerate(zip(chunks, embeddings)):
    collection.add(
        ids=[f"doc_{i}"],
        embeddings=[embedding],
        documents=[chunk],
        metadatas=[{"source": "bab-08.pdf", "page": i+1}]
    )

print(f"Collection count: {collection.count()}")
💡 Best Practice: Simpan metadata yang kaya (sumber, halaman, tanggal, judul dokumen) di vector store. Metadata ini sangat berguna untuk filtering dan source attribution saat retrieval.

8.4 Retrieval Pipeline

Retrieval Pipeline berjalan real-time saat user mengirimkan query. Pipeline ini mengambil chunk paling relevan dari vector store untuk digunakan sebagai konteks LLM.

8.4.1 Query Embedding

Query user di-embedding menggunakan model yang sama dengan yang digunakan saat indexing. Ini penting agar query dan chunk berada di ruang vektor yang sama.

def embed_query(query, model="text-embedding-3-small"):
    response = client.embeddings.create(
        model=model,
        input=query
    )
    return response.data[0].embedding

query_embedding = embed_query("Apa itu RAG?")

8.4.2 Retriever Strategies

a) Similarity Search

Mencari top-K chunk dengan cosine similarity tertinggi terhadap query embedding. Ini adalah strategi paling dasar dan paling umum digunakan.

def similarity_search(query_embedding, collection, top_k=5):
    results = collection.query(
        query_embeddings=[query_embedding],
        n_results=top_k
    )
    return results["documents"][0]

contexts = similarity_search(query_embedding, collection, top_k=5)

b) Maximal Marginal Relevance (MMR)

MMR menyeimbangkan relevansi dengan diversitas. MMR memilih chunk yang relevan tetapi tidak terlalu mirip satu sama lain, menghindari redundansi informasi.

def mmr_search(query_embedding, chunk_embeddings, chunks, 
               top_k=5, lambda_param=0.5):
    """
    lambda_param: 1 = pure relevance, 0 = pure diversity
    """
    selected = []
    remaining = list(range(len(chunks)))
    
    while len(selected) < top_k and remaining:
        mmr_scores = []
        for idx in remaining:
            # Relevance to query
            relevance = cosine_similarity(
                [query_embedding], [chunk_embeddings[idx]]
            )[0][0]
            
            # Max similarity to already selected
            max_sim = 0
            if selected:
                max_sim = max(
                    cosine_similarity(
                        [chunk_embeddings[idx]], [chunk_embeddings[s]]
                    )[0][0]
                    for s in selected
                )
            
            mmr = lambda_param * relevance - (1 - lambda_param) * max_sim
            mmr_scores.append(mmr)
        
        best_idx = remaining[np.argmax(mmr_scores)]
        selected.append(best_idx)
        remaining.remove(best_idx)
    
    return [chunks[i] for i in selected]

contexts = mmr_search(query_embedding, embeddings, chunks, top_k=5)

c) Similarity Score Threshold

Hanya mengambil chunk dengan similarity score di atas threshold tertentu. Ini mencegah LLM menerima konteks yang tidak relevan.

def threshold_search(query_embedding, collection, 
                     similarity_threshold=0.7, max_k=10):
    results = collection.query(
        query_embeddings=[query_embedding],
        n_results=max_k,
        include=["distances"]
    )
    
    # Filter berdasarkan threshold (distance → similarity)
    filtered = []
    for doc, distance in zip(results["documents"][0], 
                              results["distances"][0]):
        similarity = 1 - distance  # untuk cosine distance
        if similarity >= similarity_threshold:
            filtered.append(doc)
    
    return filtered

contexts = threshold_search(query_embedding, collection, threshold=0.7)

8.4.3 Re-ranking (Optional)

Setelah retrieval, chunk dapat di-re-rank menggunakan model cross-encoder yang lebih akurat (tapi lebih lambat). Strategi umum: retrieve banyak kandidat dengan bi-encoder (cepat), lalu re-rank top-N dengan cross-encoder (akurat).

from sentence_transformers import CrossEncoder

reranker = CrossEncoder('cross-encoder/ms-marco-MiniLM-L-6-v2')

def rerank(query, contexts):
    pairs = [[query, ctx] for ctx in contexts]
    scores = reranker.predict(pairs)
    ranked = sorted(zip(contexts, scores), key=lambda x: x[1], reverse=True)
    return [ctx for ctx, score in ranked]

# Retrieve 20 candidates, re-rank to top 5
candidates = similarity_search(query_embedding, collection, top_k=20)
top_contexts = rerank("Apa itu RAG?", candidates)[:5]

8.5 Generation

Tahap terakhir: chunk yang ter-retrieve disusun ke dalam prompt template bersama query user, lalu dikirim ke LLM untuk menghasilkan respons final.

8.5.1 Prompt Template dengan Context

Prompt harus di-desain dengan hati-hati agar LLM:

  • Hanya menggunakan informasi dari konteks yang diberikan
  • Mengakui jika konteks tidak cukup untuk menjawab
  • Menyertakan sitasi atau sumber
RAG_PROMPT_TEMPLATE = """Anda adalah asisten AI yang menjawab berdasarkan 
konteks yang diberikan. Gunakan HANYA informasi dari konteks di bawah ini.
Jika konteks tidak mengandung jawaban, katakan "Saya tidak menemukan 
informasi yang cukup untuk menjawab pertanyaan ini."

Konteks:
{context}

Pertanyaan: {question}

Jawaban (sertakan sumber dari konteks jika relevan):"""

def generate_rag_response(query, contexts, llm_model="gpt-4o"):
    context_text = "\n\n---\n\n".join(contexts)
    prompt = RAG_PROMPT_TEMPLATE.format(
        context=context_text,
        question=query
    )
    
    response = client.chat.completions.create(
        model=llm_model,
        messages=[{"role": "user", "content": prompt}],
        temperature=0.3  # lebih deterministik untuk factual Q&A
    )
    
    return response.choices[0].message.content

answer = generate_rag_response("Apa itu RAG?", contexts)
print(answer)

8.5.2 Source Attribution

Untuk transparansi, sertakan metadata sumber dalam prompt dan minta LLM untuk men-sitasi sumbernya.

RAG_PROMPT_WITH_SOURCES = """Anda adalah asisten AI yang menjawab berdasarkan 
konteks. Setiap pernyataan faktual HARUS menyertakan nomor sumber dalam 
kurung siku [1], [2], dst.

Konteks:
[1] {source_1_title}: {source_1_content}
[2] {source_2_title}: {source_2_content}
...

Pertanyaan: {question}

Jawaban (dengan sitasi sumber):"""

def generate_with_citations(query, contexts_with_metadata):
    # Bangun konteks dengan penomoran sumber
    context_parts = []
    for i, ctx in enumerate(contexts_with_metadata, 1):
        source = ctx["metadata"].get("source", f"Dokumen {i}")
        context_parts.append(f"[{i}] {source}: {ctx['content']}")
    
    prompt = RAG_PROMPT_WITH_SOURCES.format(
        context="\n\n".join(context_parts),
        question=query
    )
    # ... call LLM as usual

8.6 Best Practice Chunking

Chunking adalah salah satu aspek paling kritis dalam RAG. Chunk yang terlalu kecil kehilangan konteks; chunk yang terlalu besar menurunkan presisi retrieval.

Best PracticePenjelasan
Gunakan chunk size 256–1024 tokenSesuaikan dengan max context embedding model. text-embedding-3-small: max 8191 token, tapi 512–1024 token memberikan keseimbangan presisi dan konteks optimal.
Overlap 10–20%Overlap menjaga kontinuitas informasi di batas chunk. Terlalu besar: redundansi. Terlalu kecil: informasi hilang.
Hormati batas semantikJangan potong kalimat/paragraf di tengah. Gunakan recursive splitting dengan separator "\n\n", "\n", ". ".
Pertahankan metadataSimpan judul dokumen, section header, nomor halaman sebagai metadata setiap chunk.
Pertimbangkan chunk hierarchySimpan parent chunk (lebih besar) bersama child chunk. Saat retrieval, ambil parent untuk konteks lebih luas.
Eksperimen & evaluasiTidak ada satu ukuran untuk semua. Uji berbagai chunk size dan strategy pada dataset Anda sendiri.
Preprocessing dokumenBersihkan teks: hapus header/footer berulang, normalisasi whitespace, ekstrak teks dari PDF dengan benar.

8.7 Ringkasan

  • RAG menggabungkan retrieval dengan generation untuk mengatasi halusinasi, knowledge cutoff, dan kebutuhan domain-specific knowledge.
  • Arsitektur RAG terdiri dari tiga pipeline: Indexing (chunking → embedding → vector store), Retrieval (query embedding → similarity search → context), dan Generation (prompt template + context → LLM).
  • Chunking strategies: Fixed-size (sederhana), Semantic (berbasis makna), Recursive (hierarkis). Pilih berdasarkan jenis dokumen dan use case.
  • Retriever: Similarity search (dasar), MMR (diversitas), Similarity threshold (filter relevansi). Re-ranking dengan cross-encoder meningkatkan akurasi.
  • Best practice chunking: 256–1024 token, overlap 10-20%, hormati batas semantik, simpan metadata kaya, lakukan evaluasi iteratif.
